# 試作: カット専用モード・高速MP4書き出し（2段階の検証）

本格開発の前に、次の2つを試作して測った。既存の書き出し（ショート・字幕つき）は変えていない
（1108 の6本で、構成〈timeline〉が安定版 558e945 と同じことを確認）。

## 第1段階: カット専用モード（試作）

- 「編集の種類」で「カットのみ（試作）」を選ぶ。字幕・BGM・ズーム・オープニングは使わない。
- 大事な場面を選ぶのではなく、**要らない所だけを除く**（`js/cutonly.js` の `planRemoveOnly`）。
  言い間違い・撮り直しの前の話・意味のない間は除き、ほかの話はすべて残す。
- 音声認識は1回だけ（3回 → 1回）。`?asr=full` を付けると3回のまま。

| 素材 | 解析（1回/3回） | 完成の長さ（AI/手動） | 手動版との重なり | 失った声 |
|---|---|---|---|---|
| 1106（3本） | 34.7秒 / 58.7秒 | 58.7秒 / 56.2秒 | 92.9% | なし |
| 1107（3本） | 23.8秒 / 46.8秒 | 42.8秒 / 44.5秒 | 91.4% | **0.5秒（1回のみ）** |
| 1108（6本） | 25.6秒 / 55.2秒 | 54.7秒 / 52.8秒 | 94.0% | なし |

1107 の1回認識は、くり返した「それから」を除く位置が 0.6秒ずれて「修正」の頭を切った（3回なら起きない）。
対策の案: 言い間違い・撮り直しを除く文だけ、3回で読み直す。

## 第2段階: 再エンコードしない高速書き出し（試作）

`js/fastcut.js`・`js/mp4write.js`（試験: `tests/e2e/fastcut.mjs`）。→ アプリへの組み込みは下の「アプリへの試験的な組み込み」。

- 残す範囲のうち、キーフレームからキーフレームまでは元の映像のコマをそのまま写す（画質・色は元のまま）。
- 範囲の頭と終わり（キーフレームまでの端）だけ、デコードしてエンコードし直す。音声（AAC）は写す。
- 写した部分とエンコードし直した部分は設定（SPS・PPS）が違うため、キーフレームの前に設定を入れる。

同じカット（第1段階の構成）で、今の書き出しと比べた（PC・Chromium）:

| 素材 | 今の書き出し | 高速（1080×1920） | 高速（512×910） | 写したコマ |
|---|---|---|---|---|
| 1107（42.8秒・26範囲） | 200秒 | 15秒 | 7秒 | 44% |
| 1108（54.7秒・19範囲） | 195秒 | 11〜14秒 | 6秒 | 69% |

- コマ: 数は期待どおり。写したコマは元と同じ。エンコードし直したコマは 50〜53dB（見た目では区別できない）。
  1080×1920 ではずれたコマ 0。512×910 では各2コマ（デコーダーが最初に落とすコマ）を前のコマで埋めた。
- 音声のずれ: 範囲ごとに最大 21ミリ秒・中央 9ミリ秒（AAC の1コマの長さ以内）。
- メモリ: 60〜230MB（動画全体をメモリで組み立てるため。長い動画では端末内のファイルに少しずつ書く作りが必要）。
- 大きさ: 元の動画と同じ画質なので、元の動画のビットレートのまま（16Mbps で 55秒 → 109MB）。

### 分かった制限

- **iPhone での再生は未確認**。Chromium では再生でき、ffmpeg でもすべてのコマを読めた。
  設定を MP4 の「サンプルの説明」で分ける方式は、Chromium ではデコードのエラーになった。
- HEVC（iPhone の「高効率」）: そのまま写す部分は確認できた（コマが元と同じ）。エンコードし直す部分は、
  この PC の Chromium が HEVC のエンコードに対応していないため試せていない。
- HDR（HLG・PQ）は対象外（エンコードし直した部分だけ色が変わるため。今の書き出しを使う）。
- 動画の大きさ・向き・形式がそろっていること。切り抜き・字幕・ズームは使えない。
- 速くなる割合は、範囲の長さとキーフレームの間隔で決まる（範囲が短いほど、エンコードし直す割合が増える）。

## アプリへの試験的な組み込み（カットのみ・高速書き出し）

「カットのみ（試作）」を選ぶと、書き出しの設定に「高速書き出し（試作・カットのみ）」が出る（最初は ON）。
外すと今までの書き出しになり、同じ構成で比べられる。今までの書き出しは消していない。

### しくみ

1. 映像: キーフレームの間は元のコマをそのまま使い、つなぎ目の近くだけエンコードし直す（`fastCutVideo`）。
   コマの時刻は毎秒30コマの格子にのせる（MP4 に書くときに丸められて、2つのコマが同じ時刻になるのを防ぐ）。
   オープン GOP（iPhone の HEVC など）で、キーフレームの前に表示されるコマは、終わりのエンコードし直しに含める。
2. 音声: 今までの書き出しと同じ作り方（音量・つなぎ目のクロスフェード・BGM・最後のフェード）。`assembleOutput` に
   映像のコマを直接渡す（区間のファイルは作らない）。同じ構成で、今までの書き出しの音声と一致（相関 1.00）。
3. 書き出したあとの確かめ: つなぎ目（写した部分・エンコードし直した部分の始まり）のキーフレームを、この端末のデコーダーで
   読み、元の動画のコマ（またはエンコーダーに渡したコマ）と比べる。読めない・25dB 未満なら、完成とせず今までの書き出しにする。

### 使える条件（すべて満たすとき）

- 編集の種類が「カットのみ」で、「高速書き出し」が ON
- 字幕・ズーム（実際に寄る場面）・冒頭のタイトルがない（BGM は使える）
- 画面の切り抜きがいらない（縦横の比率が 9:16 の動画）
- 映像が H.264 または HEVC・SDR（BT.709 など）・毎秒29〜31コマ・コマの間隔に大きな空きがない
- 複数の動画は、大きさ・向き・映像の形式がそろっている
- この端末のエンコーダーが、元の動画と同じ形式でエンコードできる
- 書き出したあとの確かめに合格する

### 使えないとき（自動で今までの書き出しにする。理由は「演出」の欄と診断情報に出る）

| 場合 | 試した結果（PC・Chromium） |
|---|---|
| HDR（HLG・PQ） | 今までの書き出しに切り替え（「HDR の動画です」） |
| 毎秒60コマ | 切り替え（「毎秒60.0コマです」） |
| 大きさの違う動画の組み合わせ | 切り替え（「大きさ・向き・映像の形式がそろっていません」） |
| 書き出した動画のつなぎ目が読めない（設定を入れない壊れた動画を作って試験） | 確かめで見つけて切り替え |
| 確かめで不一致（試験用の印） | 切り替え |
| 字幕・ズーム・冒頭のタイトル・ショートのモード | 最初から今までの書き出し |

### 今までの書き出しとの違い

- 映像の最後の黒いフェード（0.9秒＋黒い画面0.2秒）は入らない（音声は同じように小さくして終わる）
- 解像度は元の動画のまま（今までの書き出しは 1080×1920 にそろえる。512×910 の動画は拡大していた）
