# Amity AI動画編集

iPhoneだけで使える、自分専用のYouTube動画編集ツールです。
美容師のカット解説動画から、**約60秒・縦9:16・日本語字幕付きのYouTubeショート**を自動で作ります。

## しくみ

GitHub Pages は「ファイルを置くだけ」のサーバーなので、編集処理はすべて **iPhoneのSafariの中** で行います。
動画はどこにも送信されず、追加のクラウド契約や費用はかかりません。

| 処理 | 方法 | 状態 |
| --- | --- | --- |
| 動画の読み込み | [Mediabunny](https://mediabunny.dev/)（`vendor/`）で、ファイルの必要な部分だけを読む | パソコンで確認 |
| 無音・長い間のカット | 音量（50msごと）から声の区間を検出。弱い語尾まで残し、長い間は自然な長さ（約0.4〜0.6秒）に縮める。つなぎ目は音をなめらかに入れ替える | パソコンで確認（v0.7） |
| 言い直しの検出 | 文字起こし結果で、似た発言のくり返し・「言い直します」等を検出 | 簡易版 |
| 重要な場面を残す | 手元の動きの量（約1秒ごとのコマの差）＋美容用語で点数をつける | 簡易版 |
| 約60秒・9:16 | 点数の高い場面を時系列で並べ、動きのある位置で縦に切り抜く | パソコンで確認 |
| 日本語字幕 | 端末内のWhisper（[Transformers.js](https://huggingface.co/docs/transformers.js)）。美容用語の辞書と、音声で確かめてから直す用語修正 | パソコンで確認（既定はOFF。失敗しても字幕なしで続行） |
| 字幕のタイミング | Whisper の時刻を、細かい発話検出で声の出始め・終わりに合わせ、カット後の時刻に変換 | パソコンで確認 |
| 字幕の手直し | 文字の修正・表示の開始/終了を0.1秒ずつ・全体のずらし・その部分の音声を再生。自動保存してMP4に反映 | パソコンで確認 |
| 字幕のデザイン | 白のゴシック体・最大2行・薄い影・フェード。手元に重ならない上/下に配置。言葉の途中で改行しない | パソコンで確認（書き出し時にON/OFF） |
| 自然なズーム | 手元がまとまって動く2秒以上の場面だけ、ゆっくり1.03〜1.08倍。10秒以上あけ、手元が切れる場合はしない | パソコンで確認（書き出し時にON/OFF） |
| MP4書き出し・保存 | WebCodecs（H.264/AAC）で1080×1920のMP4を作り、共有メニューから写真に保存。約8秒ごとの区間に分けて端末内に保存しながら書き出す | パソコンで確認 |
| 途中から再開 | Safariを閉じると一時停止。もう一度開くと、保存してある解析結果・書き終えた区間を使って続きから再開 | パソコンで確認（v0.8） |

「パソコンで確認」= パソコン上のChromeでのテストで動作確認済み。**iPhone実機では v0.3 の修正後まだ確認していません。**
iOS 26 以降の Safari が必要です。

## メモリを抑える工夫（v0.3）

iPhone の Safari はメモリが足りなくなると、エラーを出さずにページを再読み込みします（v0.2 で4K縦動画の処理中に発生）。

- ファイルは一部ずつ読む（`BlobSource` の stream reader を使わない。キャッシュ 8MB）
- 映像は自前の `VideoDecoder` で1コマずつ展開してすぐ閉じる。先読みは数コマまで
- コマは「切り抜き＋縮小」だけで canvas に描き、回転は描いた後の画像に対して行う
  （変換をかけた canvas に動画のコマを直接描くと、コマのメモリが解放されず増え続けることがあった）
- 動きの解析は 96×54 に縮小した画像で行い、書き出しは 1080×1920 固定
- 音声は少しずつ読み、文字起こし用の 16kHz モノラルだけを残す。文字起こしが終わったら手放す
- 処理中は `<video>` 要素から動画を外す
- 音声を WebCodecs で読めない場合は、区間ごとに小さな M4A に詰め直して Web Audio で読む

4K縦MOV（188MB・1分02秒）でのページのメモリのピーク（パソコンの Chrome で測定、GPU有効）:

| 段階 | v0.2 | v0.3 |
| --- | --- | --- |
| 音声の読み込み | 559MB | 265MB |
| 動きの解析 | 572MB | 391MB |
| 書き出し | 783MB | 560MB |

## 字幕AIの安定化（v0.4）

v0.3 までは字幕AIを実物で動かせていませんでした。v0.4 では Whisper（whisper-base・q8）を実際に動かして、次の問題を直しました。

- **メモリ**: 単語単位の時刻用の「注意の重み」を出力する形式のモデルだと、文字起こし中のページが約1.9GBに達した。
  出力しない形式（アプリが使う公式の onnx-community 版はこちらの形式のはず）では約0.9〜1.0GB。
  どちらの形式を読み込んだかを診断情報に記録する。重い「高精度（small）」は削除した
- **専門用語**: 「パネル→カネル」「毛先→下先」「量感→ローカー」などの誤りが多かった（文字の一致率 68%）。
  美容用語を並べたプロンプトを先に与え、よくある聞き間違いを補正して 81% に改善
- **文の区切り**: プロンプトを与えると Whisper が文ごとの時刻を出さなくなるため、
  「。」で文に分け、無音の切れ目（長い間ほど優先）に合わせて時刻を割り当てる
- **言い直し**: ひらがな表記（「いい直します」等）でも合図として検出。合図の前に内容がある文は、その文だけを除外
- 文字起こしが長引いたときに「字幕をスキップして続ける」ボタンで先に進める

## 字幕の精度とタイミング（v0.5）

| 項目 | v0.4 | v0.5 |
| --- | --- | --- |
| 話した内容との一致率（静かな環境） | 85.2% | 92.6% |
| 話した内容との一致率（サロンの雑音・やや早口） | — | 89.3% |
| 字幕の出始めと声の出始めの差（中央値 / 最大） | 0.33s / 16.6s | 0.02s / 0.77s |
| 字幕の終わりと話し終わりの差（中央値 / 最大） | — | 0.01〜0.04s / 0.06s |

（パソコンの Chrome、日本語の合成音声による美容解説のテスト動画 `tests/e2e/make-ja-beauty.py` で測定）

- **字幕のズレの原因**: v0.4 で精度のために与えていたプロンプトのせいで、Whisper が文ごとの時刻を出さなくなっていた。
  プロンプトをやめ、美容用語を書き始めたら続きを選びやすくする軽いバイアスに変更
- **用語の修正は音声で確かめてから**: 辞書（`BEAUTY_TERMS`）から「エリアシ→襟足」「ハネル→パネル」などの修正案を作り、
  同じ音声に対して元の文と修正案のどちらがもっともらしいかを Whisper に採点させ、基準を満たすものだけ直す。
  同じ読みの書き換えは採用、辞書の書き間違いは対数尤度の差 -6 まで、似たカタカナ語は -3 まで。強制的な置き換えはしない
- **16kHz への変換**: 単純な間引きだと高い音が折り返して雑音になり、聞き取りが悪くなっていた。低域通過フィルターつきに（`js/resample.js`）
- **表示時刻**: Whisper の文の時刻を、細かい発話検出で声の出始め・終わりに合わせる。文の中のページは読みの長さで割り振って息継ぎに合わせる。
  元の動画の時刻からカット後の時刻へは、削った無音を考慮して変換する。自動カットの区切りには使わない
- **手直し**: 構成の確認画面で、字幕の文字・表示の開始/終了（0.1秒単位）・全体のずらしを直せる。
  動画ごとに `localStorage` へ自動保存し、同じ動画をもう一度解析したときも引き継ぐ

## 編集前の入力（v0.6・第1段階）

動画を選んだ後に、次の内容を入力できます。**すべて任意**で、何も入力しなければ従来と同じ自動編集になります（同じ場面が選ばれることをテストで確認）。

| 入力 | 使い方 |
| --- | --- |
| 動画の種類 | ショート（縦9:16・1080×1920）。ロング（横16:9・1920×1080）は第5段階で対応するまで選べません |
| 完成動画の長さ | ショート: 30秒・45秒・60秒・自由入力（10〜180秒）。ロング: 5・8・10・12分・自由入力（準備中） |
| 編集スタイル | シンプル・オシャレ（初期設定）/ テンポ重視（短い場面を選びやすく、ズームの間隔 6秒・最大1.10倍） |
| タイトル・内容・流れ | 取り出した用語（例: ボブ・セニング・45度）を話している場面の点数を上げる |
| 一番伝えたいこと | 同上（重みを大きく） |
| 流れ | 段階の数（3〜8）で動画全体を区切り、各区間から場面を選ぶ。**順番は元の動画のまま** |
| 必ず残したい説明や場面 | 1行に1つ。一番合う発言を「必ず残す」にし、目標時間を超えても削らない。関連する発言と、その直後の作業場面は点数を上げる |

- 入力の言葉は、文字起こしで「書き始めたら続きを選びやすくする」用語にも加えます（強制はしない）。**入力した文が字幕に追加されることはありません**
- 確認画面に「目標 → 完成予定」を表示。収まらないときは理由（必ず残す場面だけで超える／元の動画が短い／素材が足りない／場面の区切り）を表示
- 確認画面で入力を変えたら「変更した入力内容で構成し直す」で、解析し直さずに構成だけ作り直せます
- 種類・長さ・スタイルは次回も引き継ぎ、文章の入力は動画ごとに端末内（`localStorage`）へ保存します

## 自動カットの自然さ（v0.7・第1段階）

「不自然な間が残る」「切る位置がおかしい」の原因を、実際の撮影に近い話し方のテスト動画（`tests/e2e/make-ja-natural.py`：
考えながら話す長い間・弱く消える語尾・息・ハサミの音・えーと・言い直し・「なので」で続く文）で調べて直しました。

| 原因（v0.6） | 直したこと（v0.7） |
| --- | --- |
| 文字起こしの時刻で声を切り落としていた（時刻が早く終わると語尾が欠ける・正確だと文と文の間が0秒になる） | 声の区間ごと残す。2つの文を続けて話している所だけ、境目の一番静かな点で分ける |
| 0.3秒以上の無音は、長さに関係なく約0.2秒に詰めていた | 文の中の0.5秒以下の間はそのまま。長い間は0.42〜0.6秒に（長い間ほど少し長く）。話し始めの前0.18秒・話し終わりの後0.32秒を残す。文と文の間は約0.5秒（テンポ重視は約0.35秒） |
| 小さな音（言葉の出始め・消えていく語尾）を声と見なさなかった | 大きな音で見つけた声を、小さな音が続く所まで広げる（前に最大0.3秒・後ろに最大0.45秒） |
| つなぎ目ごとに音を一度0にしていた（部屋の雑音ごと「プツッ」と途切れる） | 40msのクロスフェードで入れ替える。動画の最初と最後だけ短くフェード |
| ハサミの音を声と見なし、作業場面を細切れにしていた | 短い音がとびとびに続くだけの区間は声にしない。作業場面として残す（ハサミの音がある場面は少し優先） |
| 「えーと」だけの発言が、文字起こしのない声として残っていた | 「つなぎ言葉のみ」として除外 |
| 「なので…」で始まる文だけが残ることがあった | 前の文に続く文・「〜て、」で終わる文は前後とまとめて残すか外す。文字起こしなしでも1.2秒未満の間でつながった声はまとめる |
| — | 話していない作業場面は目標時間の40%まで（説明が削られすぎない）。言い直した後の発言は優先して残す |

書き出したMP4での評価（`tests/e2e/eval-cuts.py`。パソコンの Chromium・文字起こしは正解の文を Whisper のように少しずらした時刻で返す偽のデータ）:

| テスト動画（目標の長さ） | 語尾・頭が欠けた句 v0.6→v0.7 | 文と文の間（中央値） v0.6→v0.7 | 0.25秒未満に詰まった文の間 v0.6→v0.7 | つなぎ目で音が途切れた所 v0.6→v0.7 |
| --- | --- | --- | --- | --- |
| 自然な話し方（45秒） | 2 → 0 | 0.17s → 0.48s | 6 → 0 | 19/27 → 0/15 |
| 自然な話し方・字幕OFF（45秒） | 1 → 0 | 0.14s → 0.48s | 8 → 0 | 19/24 → 0/11 |
| 自然な話し方・テンポ重視（45秒） | 2 → 0 | 0.17s → 0.34s | 6 → 0 | 19/27 → 0/14 |
| 美容解説・静か（60秒） | 3 → 0 | 0.01s → 0.55s | 8 → 0 | 14/16 → 0/16 |
| 美容解説・サロンの雑音（45秒） | 5 → 0 | 0.01s → 0.35s | 6 → 0 | 15/15 → 0/6 |

- 文の途中で切れた文はどれも 0（v0.7 の開発途中に字幕OFFで2件出たため、上の「まとめる」処理を追加）
- 1.2秒より長い間（作業場面をはさむ所を除く）はどれも 0
- 解析・書き出しの時間とメモリは v0.6 と同じ（自然な話し方・45秒: 解析 約6秒・書き出し 約190〜210秒・ページのメモリのピーク 約610〜630MB。パソコンでの値）
- **iPhone実機ではまだ確認していません。** テスト音声は合成音声なので、実際の声で「間」が自然に聞こえるかは実機で確認が必要です

## 途中から再開（v0.8）

追加費用0円・外部サーバーなしで、iPhoneの中だけで処理する方式です。

- **Safariを閉じる・ほかのアプリに切り替える・画面を消すと、編集は一時停止します。閉じている間は進みません**
  （iPhone の Safari は、画面に出ていないページの処理を数秒で止めるため。Webページだけで処理を続ける方法はありません）
- もう一度開くと、画面上部の「途中の編集」に保存してある所までの状態が出ます。「続きから再開」で続きから進めます
- 進み具合の数字だけでなく、**処理した結果そのもの**を端末内に保存し、終わった処理はやり直しません

| 段階 | 保存するもの | 途中で止まったとき |
| --- | --- | --- |
| 元の動画のコピー | 選んだ動画を端末内の保存領域（OPFS）にコピー | 再開時に動画を選び直さなくてよい。空きが足りない・コピーが消えたときは、同じ動画を選び直す（大きさと長さで同じ動画か確かめる） |
| 音声の解析 | 50msごとの音量、文字起こし用の16kHz音声 | この段階は最初からやり直す（1分の動画で数秒） |
| 文字起こし | 約28秒の区間ごとの結果 | 保存済みの区間は飛ばす |
| 手元の動き | 約30秒ぶんごとの途中の結果 | 保存した所から続ける |
| 構成の確認 | 選んだ場面・入力内容（字幕の手直しは従来どおり別に保存） | 同じ構成を表示する |
| 映像の書き出し | **約8秒ごとの区間をMP4ファイルとして保存** | 書き終えた区間はやり直さず、書きかけの1区間だけやり直す |
| 仕上げ | 区間の映像を再エンコードせずにつなぎ、音声を最初から最後まで通して作る | 仕上げだけやり直す（1分の動画で数秒） |

進み具合と解析結果（小さなデータ）は IndexedDB に、大きなデータ（動画のコピー・区間・完成したMP4）は OPFS のファイルに書きます。
OPFS への書き込みは、古い iOS でも使える `createSyncAccessHandle()`（ワーカーの中）を使います（`js/opfs-worker.js`）。
書き出しも仕上げも、ファイルに少しずつ書くので、**動画全体をメモリに持ちません**（v0.7 までは完成した動画をメモリに持っていたため、長い動画ではメモリが足りなくなっていた）。

### 保存に必要な容量と、足りないとき

| 必要なもの | 目安 |
| --- | --- |
| 元の動画のコピー | 元の動画と同じ大きさ（iPhone の4K・1分で約200MB、15分で約1.5〜3GB） |
| 文字起こし用の音声（文字起こしが終わったら消す） | 1分あたり約4MB |
| 書き出した区間＋完成したMP4（完成したら区間は消す） | 完成した動画1分あたり約150MB × 2 |

- 書き出す前に、ブラウザが見積もった残りの容量と比べ、足りなければ書き出しを始めずに必要な量と空きを表示します
- 元の動画をコピーする空きがなければ、コピーせずに進めます（再開するときは動画を選び直す）
- 書き出しの途中で空きがなくなったときは、書き終えた区間を残したまま一時停止し、空きを増やしてから再開できます
- 途中経過を保存できなかったときは、編集は続けたまま、その旨を表示します（途中で止まると最初からになる）

### 保存データが消えることへの備え

保存データは必ず残るとは限りません（iPhone の空き容量不足、Safari の「履歴とWebサイトデータを消去」、長期間使わない場合など）。

- 画面に警告を出し、元の動画は写真アプリに残しておくこと、完成したら早めに保存することを案内します
- 消されにくくするよう、ブラウザに保存の継続（`navigator.storage.persist()`）をお願いします（認められるとは限らない）。ホーム画面に追加して開くと消えにくくなります
- 再開するときは、保存したはずの区間が残っているか確かめ、消えていた区間だけ書き出し直します。完成した動画が消えていたら、構成はそのまま書き出し直せます
- 「保存データを削除」で、作業ごとに保存データを消せます（元の動画は消えません）

### 検証結果（パソコンの Chromium・4コア。ブラウザのプロセスを強制終了して再開）

途中でブラウザを強制終了し（後片付けの処理が一切動かない、Safari が落ちたときに近い止め方）、もう一度開いて「続きから再開」を押した（`tests/e2e/resume.mjs`）。

**1分の動画（1分24秒の素材 → 約43秒）**: 途中で止めずに書き出した場合は、解析 約6〜7秒・書き出し 約142〜151秒・ページのメモリのピーク 約590〜650MB（v0.7 は 約190〜210秒・610〜630MB）

| 止めた所 | 再開したときの動き | 結果 |
| --- | --- | --- |
| 手元の動きの解析（36%） | 音声・文字起こしは保存した結果を使い、動きは36%から続けた | 完成 |
| 文字起こし（3区間中1区間を保存） | 残りの区間だけ文字起こし | 完成 |
| 書き出し（7区間中2区間を保存） | 2区間を再利用し、残り5区間を書き出した | 完成 |
| 書き出しで2回（2区間・4区間を保存した後） | 3回に分けて処理し、2区間・4区間を再利用 | 完成 |
| 仕上げ（区間をつなぐ途中） | 7区間すべてを再利用し、仕上げだけ（3秒） | 完成 |
| 書き出し（3区間を保存）＋元の動画のコピーを削除 | 「同じ動画を選び直してください」と表示 → 選び直すと3区間を再利用 | 完成 |

- どの場合も、完成したMP4は 1278コマ（42.6秒）・音声と映像の長さが一致・デコードのエラーなし

### 技術的な制約

- **閉じている間は処理が進みません**（一時停止と再開。バックグラウンドで続ける方式ではありません）
- 再開のときに、止まった区間（最大約8秒ぶん）と、音声の解析・仕上げは最初からやり直します
- 区間をつなぐには、区間ごとの映像の形式（H.264 の設定）が同じである必要があります。違った場合は、区間に分けずに一度で書き出し直します（その場合は途中から再開できません）。
  パソコンの Chromium では一致しました。iPhone のエンコーダーで一致するかは実機で確認が必要です
- 画面を離れた直後に戻ったとき、エンコーダーが止められていることがあるため、その区間は1回だけ自動でやり直します
- 区間ごとのエンコードのため、区間の境目で画質の変化はほとんどありませんが、区間の始まりは必ずキーフレームになります（ファイルが少し大きくなる程度）
- **iPhone 実機ではまだ確認していません**（OPFS・IndexedDB・共有メニューへの大きなファイルの受け渡し）

## iPhone実機の不具合の修正と、言い直し・くり返しの判断（v0.8.1）

iPhone実機で、v0.8 の書き出しが途中で「EncodingError: Decoder failure」で止まり、「途中の編集」が出ずに再開できなかった。

### 書き出しの失敗（EncodingError: Decoder failure）

iPhone 実機がないため、原因は特定できていない。調べた結果、可能性の高い順に次のとおりで、それぞれに対処した。

| 考えられる原因 | 根拠 | 対処 |
| --- | --- | --- |
| 書き出し中に画面が消えた・ほかのアプリに切り替えた | iOS は画面に出ていないページの映像デコーダーを止める。v0.8 は1回だけすぐにやり直していた（画面が消えたままだと、また失敗する） | 画面を離れたら区間の途中で一時停止し、戻ったらその区間から書き出し直す（失敗にしない） |
| HEVC（iPhone の「高効率」）で、キーフレームより前に表示されるコマ | キーフレームから始めると、前のまとまりを参照するコマは正しくデコードできない。HEVC の open GOP の動画（168コマ該当）で、v0.8 は WebKit で再開後に止まった | そのコマはデコーダーに送らない（表示時刻がキーフレームより前なので、出力には使わない） |
| 区間ごとに作り直す canvas（1080×1920）のメモリ | iPhone では使い終わった canvas のメモリ（GPU）がすぐに解放されない | 書き出し全体で使い回す |
| その他（一時的なデコーダーの失敗） | — | 同じ区間を、作り直したデコーダーで1回、低遅延モードなし・1つ前のキーフレームからでもう1回、やり直す |

失敗したときは、**区間・コマの位置・元の動画の時刻・キーフレーム・送ったコマの数・入力のコーデック・デコーダーの状態・段階（デコード／描画／エンコード／ファイルの読み書き）**を診断情報と保存データに記録する。

調べる途中で、WebKit（Safari と同じエンジン）の音声エンコーダーが、AAC のフレームに同じ時刻を付けて返すことを見つけた（MP4 の音声の時刻が壊れる）。
音声は内蔵の AAC エンコーダー（FFmpeg の WASM 版）で作るようにした。

### 途中から再開できなかった

- **Safari とホーム画面に追加したアプリは、iPhone では保存場所が別**。片方で始めた編集は、もう片方には出ない。画面に、今どちらで開いているかと、同じ方法で開くよう表示した
- 端末内への保存に `createSyncAccessHandle` が使えない環境では、`createWritable`（Safari 26 以降）を使うようにした（WebKitGTK では前者が使えず、v0.8 は保存に失敗していた）
- 保存した作業の控えを localStorage にも残し、保存データを読めないときは「続きから再開できません」と理由（読み込みの失敗・保存の失敗・消えた）を表示する。保存データは勝手に消さない
- 書き出しに失敗しても、書き終えた区間と編集の設定を残し、「途中の編集」から失敗した区間だけやり直せる
- 保存の失敗・読めなかった作業・書き込みの方式（sync / stream）・開いた場所（Safari / ホーム画面）を診断情報に記録する

### 言い直し・くり返しを、話した内容から判断する（`js/content.js`）

| 判断 | 例 | 扱い |
| --- | --- | --- |
| 訂正の合図で始まる文 | 「ここを軽くします。」→「いや、ここじゃなくて、耳後ろを軽くします」 | 前の発言を外し、「いや、ここじゃなくて、」を取り除く |
| 文の途中の訂正 | 「スライスは、一センチ、すみません、二センチの幅で取ります」 | 言い間違えた句と合図だけを取り除き、前の句は残す |
| 同じ説明を続けて2回 | 「パネルを45度に引き出して、カットします」×2 | 前の方を外す（用語がまったく同じときだけ） |
| 文の中のくり返し | 「このパネルを、このパネルを、90度で…」 | 前の「このパネルを、」を取り除く |
| 同じ用語で別の技術 | 「サイドは…45度…」「バックも…45度…」、「0度」と「45度」 | **外さない** |

- 文の一部を取り除くのは、その位置に声の切れ目（0.08秒以上）があるときだけ。なければ文の途中では切らず、候補として表示する
- 文字起こしの間違いを根拠に必要な説明を削らないよう、確かでないもの（あとの文に用語が加わっている・用語が1文字違い・訂正の合図がおわびかもしれない）は外さずに、確認画面に「候補」として出す
- 確認画面で、取り除いた部分は「元に戻す」、候補は「この部分を取り除く」で切り替えられる（選んだ内容は保存され、再開しても残る）

### 字幕の正確さ（最優先）

| 原因（調べて分かったこと） | 直したこと |
| --- | --- |
| 字幕AI（ReazonSpeech）の誤りのほとんどは「言葉を落とす」こと。どこで落とすかは、読む音声の区切り方で大きく変わる（同じ音声で誤り率 3〜35%）。文の途中で区切った窓・長い無音をはさむ窓で落としやすい | 区切り方の違う3通り（30秒ごと／15秒ずらした30秒ごと／0.5秒以上の間で分けたまとまり）で読み、文字の並びを照らし合わせて、どれかが落とした言葉をほかの結果から差し込む（`asrWindows`・`mergeAsrPasses`） |
| 声の区間を0.1秒の間でも分けていたため、続けて話す音声では言葉の途中（「トッ｜プ」）で窓が区切られていた | 0.3秒より短い間では区切らない |
| 読んだ音声の最初の文字の時刻を音声の頭にするため、計算の誤差で文の1文字目が落ちることがあった | 音声の頭の文字も受け取る |
| 同じ読みの別の漢字（根元布巾・痛んで）、ひらがなの1文字違い（つかないで） | 入力した用語・タイトルのひらがな・髪の話でよく間違える漢字（傷む）に合わせて直し、確認の印をつける。「前上がり／前下がり」のような1文字違いは直さない |
| 否定の言葉（しない・ません）を落とすと意味が逆になる | 3通りの聞き取りで否定の言葉・入力した用語の有無が違う文、文の終わりが言葉の途中で終わっている文（「…は軽く」）を **要確認（赤い枠）** にする。確認するまで字幕は完成とみなさず、書き出し前に一覧を出して確かめる |
| 字幕が言葉の途中（「まと／まり」「たくさんで｜きて」「トップ／表面」「アホ毛の／ような」）で分かれる | 「〜して」「〜際に」・言い切りの形（〜ない・〜く）の後・次の文の始まり（それを・この場所）で分ける。声の間は言葉の途中では使わない。読点の1文字は1行の文字数を超えてよい。文の始まりの言葉（あとは）の途中で分かれた文は言葉の前で分ける |
| 原稿の文字の時刻は声より早くなることがある（0.65〜0.77秒早く表示） | 2ページ目からは、近くの声の出始めに合わせる |

### 言い直し・不要な発言

- 文の終わりで言いかけてやめ、次の文で同じ言葉から言い直した部分（「…なのか、トップの」）は、残す最後の文字のすぐ後の声の切れ目で取り除く
- 字幕AIが文字にしなかった声は、確かでないので自動では取り除かず、**取り除ける候補**として確認画面に出す
  （2秒未満の文字にならない声・文の後に続く声・文の途中の言いかけ「…ないと、うまくいきま、うまくカバー…」）

### 画質（同じコマを元の動画と比べた結果。`tests/e2e/quality-bench`）

- **Safari と同じエンジン（WebKit）では、縮小の補間の設定で細かさが変わる**。初期設定（v0.9.0 まで）では細かさ −16%・コントラスト −9%。
  v0.9.1 は「高品質」に指定（細かさ 16.1、初期設定 13.5）。手動編集との違い（ぼやけて・コントラストが低い）の原因の一つと考えられる。iPhone 実機では未確認
- パソコンの Chromium は指定に関係なく同じ。色・明るさ（灰色の段階・茶色系の色）は元の動画と同じ値（±1）。iPhone の縦動画と同じ形（4K・回転90度）でも同じ
- 細かさは H.264 に圧縮した段階で約80〜89%になる。パソコンの Chromium では 10Mbps・20Mbps・40Mbps でほぼ同じ。
  v0.9.0 の説明（10Mbps で66%→20Mbps で78%）と、v0.9.1 の途中の「約7%暗い」は、違うコマを比べた測定の誤りでした
- iPhone はハードウェアのエンコーダーで、HDR の動画を SDR に変換して書き出す。元の動画が HDR かどうか・エンコーダーがハードウェアかどうかを
  「診断情報」に出し、HDR のときは画面に注意を表示する。計測ページ（`tests/e2e/quality-bench.html`）は iPhone の Safari で動画を選んで
  その場で測れる（動画は端末の外に送らない）
- ズームは、元の動画の画素が足りず拡大になる場合（1080p の動画など）はしない

## 短く自然な字幕とカット精度の最終改善（v0.9.4）

固定テスト素材 IMG_5953（元の動画 67.83秒・v0.9.3 のAI編集 60.83秒・手動編集 62.47秒）で、手動編集と比べた（`tests/fixtures/img5953`）。

**字幕を「文字起こし」と別の工程にした**（`js/captions.js`）
1. 音声を文字起こしする（文字起こしの文字は、確認画面・言い直しの判断に使う。変えない）
2. 必要な説明を判断する（言い直し・くり返しのカット。これまでどおり）
3. 表示用の短い字幕にする: 文の中の調子をとる「ね」・形容詞の後の「という」・つなぎ言葉を省いてから、意味のまとまり・息継ぎ・
   話す時間で1行のページに分け、ページの頭の「なので」「そうなると」などを省く。**音声は削らない**。
   「でも」「もし」・何かを指す「それは」・否定の言葉・用語・数字は省かない
4. 話した文字の時刻に合わせて表示する

字幕の区切りは、目安5〜12文字（最大15文字は上限）・3秒以内。区切りの強さを「文の境目 > 節の境目（〜て・〜後に・〜ので・〜と）
> 助詞の後」にし、助詞から始まるページ・「名詞／する」・「と／いう」・「伸びて／重くなったボブ」のような分け方をしない。

| --- | --- | --- | --- |
| 長さ | 60.83秒 | 61.44秒 | 62.47秒 |
| 最初の言葉の前 | 0.03秒 | 0.5秒 | 1.0秒 |
| 字幕の平均文字数 | 11.2文字 | 9.2文字 | 12.4文字 |
| 字幕の平均表示時間 | 2.38秒 | 2.05秒 | 2.78秒 |
| 字幕に出た不要な言葉（ね・という・そうなると） | 6回 | 0回 | 0回 |
| 手動編集の字幕の切れ目と同じ所で切れた割合 | 68% | 95% | ― |

ほかの素材でも同じルールで確かめた（手動編集の字幕の切れ目との一致: IMG_5830 81%→88%・bob 85%→85%・ヘアカッター 67%→72%）。
カット: 文と文を静かな所で分けたときに文の終わりの余白がつかなかった不具合を直し、最初の言葉の前に0.4秒の余白をつけた。
間の詰め方は、手動編集3本の完成の長さの差が一番小さくなる値にした（3本とも ±1.1秒以内）。

`--real-asr` は、Transformers.js・ONNX Runtime・モデルの通信を手元のファイルに差し替えて、本物の Whisper で文字起こしします
（DIR には whisper-base の `config.json` などと `onnx/encoder_model_quantized.onnx`・`onnx/decoder_model_merged_quantized.onnx` を置く）。

`--real-asr` を付けない通しテストでは、文字起こしは偽のデータに差し替えています。
H.264 を扱える Chrome（Chrome for Testing、または Playwright 同梱の Chromium の新しい版）が必要です。Linux の Chrome は HEVC を読めないため、
HEVC の動画では「読み込めない」旨のメッセージが出ることだけを確認しています。
